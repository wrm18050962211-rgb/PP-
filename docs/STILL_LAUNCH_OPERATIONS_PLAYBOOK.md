# Still 上线运营与验证手册

更新日期：2026-08-04
适用范围：Still / PP 首城首发、受控运营和融资前验证。
本文不替代 [发布与技术路线图](./DUAL_PLATFORM_RELEASE_ROADMAP.md)、[Still 代码模块路线图](./STILL_CODE_MODULE_ROADMAP.md)、支付规则或法律合规意见。

## 1. 目标与原则

首发目标不是快速扩张，也不是证明功能数量，而是在一个城市、一个核心场景中证明：

```text
可信摄影师供给
-> 用户能理解套餐并愿意预约
-> 定金/订单可支付、可追踪
-> 服务可交付、售后可处理
-> 结果转化为复约、转介绍和可复核数据
```

首发遵循以下原则：

- **单城、单主场景。** 先选一个城市和一个最容易标准化的场景，例如周末城市生活方式人像或小红书出片套餐；不同时覆盖所有摄影品类。
- **人工运营优先。** 首发可人工审核摄影师、确认订单、处理退款和售后；不为自动化而推迟真实交易验证。
- **真实数据优先。** 订单、付款、履约、退款和反馈必须可回溯，不能以 mock 数据、虚构订单或刷单代替。
- **先验证价值，再做 AI。** AI 不得阻塞 TestFlight、支付、履约或基础客服；在真实偏好与订单闭环存在前，不以“有 AI”作为运营目标。
- **合规和信任是产品的一部分。** 对外运营前必须有可访问的隐私、协议、支付/退款说明、客服与举报入口。

## 2. 上线前放行门槛

只有下列项目可用，才进入真实用户运营。技术节点的完成标准以两个 roadmap 为准。

| 范围 | 最小放行标准 |
| --- | --- |
| 账户与权限 | 真实登录、会话持久化和用户/摄影师/Admin 权限边界可验证；不依赖 mock 登录。 |
| 内容与供给 | 摄影师资料、套餐和样片来自可核验的真实供给；摄影师审核由人工负责。 |
| 预约与订单 | 用户能提交预约；运营能查看、确认和追踪订单状态。 |
| 支付与退款 | 小额真实支付、服务端回调验签、订单状态持久化和人工退款流程已验证。 |
| 数据与媒体 | 生产数据库、媒体存储、备份与恢复、生产域名/HTTPS 已就绪。 |
| 风险与支持 | 隐私/协议/退款/客服/举报入口可访问；基础监控、崩溃上报与告警已生效。 |

尚未满足放行门槛时，可以做招募、访谈和内部体验，但不得将其记为公开运营或真实经营数据。

## 3. 首城运营模型

### 3.1 首发范围

首发只保留以下链路：

```text
发现样片与套餐
-> 选择摄影师 / 提交需求
-> 支付预约定金
-> 人工确认并撮合
-> 线下履约
-> 交付与拍后反馈
-> 复约或转介绍
```

暂缓全自动审核、复杂推荐算法、自动结算、提现、积分会员、补贴裂变和全品类扩张。

### 3.2 供给侧启动

1. 招募并人工审核首批 10 位左右摄影师，优先选择作品风格清晰、沟通稳定、能接受标准套餐和交付承诺的人。
2. 为每位摄影师建立可公开的套餐：适合谁、拍摄地点、时长、价格、交付张数/时间、修图范围、取消与退款规则。
3. 先限定可预约时段和服务半径，宁可减少选择，也不要出现无法履约的订单。
4. 每单结束后记录摄影师响应、准时性、取消原因、交付时效、投诉和用户反馈；该记录只服务于人工运营决策，不直接作为不透明的自动降权依据。

### 3.3 需求侧启动

1. 将首页和对外内容表达为“场景 + 风格 + 可预约套餐”，而非泛摄影黄页。
2. 早期获客优先使用摄影师自有作品/社媒、朋友转介绍、城市生活方式社群和小范围内容测试。
3. 每条线索必须进入统一记录：来源、需求场景、预算、是否咨询、是否支付定金、取消原因和后续反馈。
4. 不以大额投放换取表面注册量；先确认用户是否理解套餐、愿意支付和愿意推荐。

## 4. 每单运营 SOP

| 节点 | 运营动作 | 必留记录 |
| --- | --- | --- |
| 咨询 | 确认城市、日期、场景、预算、参考风格与联系方式。 | 线索来源、需求摘要、负责人。 |
| 报价与下单 | 指向明确套餐；告知定金、取消、退款、交付和客服规则。 | 套餐版本、报价、订单状态。 |
| 支付后 | 人工核验支付状态，与摄影师确认档期和服务边界。 | 支付状态、确认时间、双方确认。 |
| 拍摄前 | 收集少量主动提供的参考图和拍摄偏好；形成订单需求快照。 | 授权范围、需求快照、地点/时间。 |
| 履约 | 处理迟到、改期、取消和安全问题；必要时升级负责人。 | 事件、处理过程、结果。 |
| 交付 | 核对交付内容、时限和修图范围。 | 完成时间、交付确认、售后记录。 |
| 拍后 | 收集满意度、问题、愿不愿意复约/推荐。 | 评分、文字反馈、复约意愿。 |

## 5. 运营节奏与验证闸门

下面的数字是首发运营目标，用于决定下一步投入，不是可以包装或替代真实收入的融资承诺。

| 阶段 | 周期 | 目标 | 放行判断 |
| --- | --- | --- | --- |
| 内部验证 | 上线前 | 跑通账号、预约、支付、订单、退款和客服链路。 | 无真实支付/履约时不得对外宣称已运营。 |
| 首批验证 | 上线后 1–4 周 | 约 10 笔真实定金订单，至少 5 笔完成履约并收集反馈。 | 证明核心服务闭环，而非追求规模。 |
| 可复用验证 | 后续 4–8 周 | 约 30 笔完成付费订单、10 位以上活跃摄影师，并持续记录订单趋势和单位经济。 | 开始正式准备天使/Pre-seed 融资材料。 |
| 增长验证 | 数据稳定后 | 比较不同场景、渠道与套餐的转化、履约与复约。 | 只扩张已被证明的城市/场景组合。 |

## 6. 核心指标看板

每周固定更新，所有数据应可追溯到订单、支付、客服或调研原始记录。

| 维度 | 指标 |
| --- | --- |
| 供给 | 审核通过摄影师数、活跃摄影师数、可预约时段、接单响应率、履约完成率。 |
| 需求 | 有效咨询数、咨询到定金转化率、订单来源、获客成本。 |
| 交易 | 已支付定金数、完成付费订单数、GMV、平台收入、退款/取消率。 |
| 服务 | 交付准时率、投诉/纠纷率、平均沟通时长、满意度。 |
| 留存 | 复约率、转介绍率、常约摄影师比例。 |
| 单位经济 | 单笔平台收入、支付/获客/客服成本、单笔贡献毛利。 |

## 7. 偏好档案与 AI 试点

### 7.1 正确顺序

依照 roadmap，先完成非 AI 偏好档案与真实订单反馈闭环，再开展 AI：

```text
结构化偏好 + 少量主动选择的参考图
-> 订单需求快照
-> 摄影师在授权范围内查看
-> 拍后反馈
-> 验证沟通与满意度改善
-> 文字优先的 AI 偏好助手
-> 经验证后再试点有限图片理解
```

### 7.2 首个 AI 试点

首个试点应为文字优先、用户可确认的“个人摄影偏好助手”：

- 为用户追问缺失信息，并整理成可编辑的拍摄 brief；
- 基于已授权的偏好和当前订单，生成摄影师可见的必要需求摘要；
- 生成复约草稿，不自动代替用户下单、修改价格或作出权益决定；
- 只在用户主动选择时分析少量图片，不批量读取系统相册；
- 禁止颜值/外貌评分、敏感属性推断和以 AI 分数自动处罚摄影师。

试点应设置非 AI 对照组，并同时比较咨询到定金转化率、平均沟通时长、取消/纠纷率、满意度和复约率。没有改善数据时，不扩大 AI 成本或宣传为核心壁垒。

## 8. 运营边界

- 不使用个人收款码长期收取平台订单款；资金、发票和凭证处理遵循 [公司财税合规手册](./COMPANY_FINANCE_COMPLIANCE.md)。
- 不虚构订单、用户、摄影师、评价或支付数据。
- 不在代码仓库保存用户原图、身份证明、支付信息、聊天记录或其他敏感经营资料。
- 用户可以不建立长期偏好档案；授权、撤回、保留和删除规则必须可见、可执行。
- 若发生安全、重大投诉、支付异常或数据事件，先止损、保留记录并按生产 Runbook 升级处理。
